# 歌词候选匹配、手选与缓存

> 最近核对：2026-11-13。本文描述当前实现；第 11 节单独列出尚未实现的统一决策。源码主要位于 `Stanza/Services/Lyrics/`，人工列表过滤位于 `Stanza/LyricsPickerWindow.xaml.cs`。

## 1. 当前范围

- 输入统一为 `LyricsQuery`，携带标题、歌手、时长及专辑等上下文；QQ 搜索和评分已传递 `query.Album`，不再是散参数接口或“专辑尚未接入”。
- 自动加载仍按 **QQ → 网易云 → LRCLIB** 串行回退，首个 Loaded / Instrumental 提供器结束链路。
- 各提供器内部评分与选取，手动列表再聚合所有已取得的候选。**聚合手动候选不等于自动跨源统一决策已经完成。**
- 元数据匹配度只说明“像不像目标歌曲”，不说明候选一定有歌词、能成功获取或解析。

## 2. 自动候选：歌名准入、歌手分档、综合排序

QQ 的生产入口为 `PrepareAutoCandidates`：

1. 歌名符合 `TitlesRelated` **或**严格核心歌名判定 `IsSameSongTitle`，才能进入自动候选。
2. 按 `ArtistRankKey` 降序、综合分降序、原始顺序排序。
3. 若有期望歌手且存在歌手分达到 `0.6` 的候选，只保留该档；一个也没有时降级使用全部歌名相关候选，不得整源放弃。
4. 最多尝试 `MaxAutoAttempts = 4` 个候选；遇到纯音乐继续寻找有歌词的候选，保留原有兜底行为。

**歌手分档不是全源一票否决。** QQ、网易云、LRCLIB 共用的歌手分档选择必须保留没有匹配歌手时的降级通道。

## 3. 手动列表：聚合与展示分开

`LyricsProviderChain.GetCandidatesAsync` 保留提供器返回的候选，并重新标注 `TitleMatched`，排序为：

```text
TitleMatched → ArtistMatched（true > null > false）→ MatchScore → 原始顺序
```

选择窗口的展示规则：

- 始终排除 `TitleMatched == false`，其他歌曲不能通过勾选重新出现。
- 默认若有明确匹配歌手的同名候选，隐藏明确不匹配的歌手；信息未知项保留。
- “显示其他歌手的同名版本”仅放宽歌手限制，仍受歌名过滤。
- 没有匹配歌手时保留同名结果，避免艺名/别名差异堵死纠错通道。
- 无相关结果时提示重搜，不再提供“显示全部搜索结果”。

提供器层保留搜索结果，不代表 UI 必须无条件显示全部；两者职责不能混淆。

## 4. 搜索召回不等于同曲判定

`TitlesRelated` 是历史自动召回规则：忽略空白和大小写后，相等成立；只有双方较短标题至少 2 字时，才允许包含关系。单字“星”不能吸到“星炬不熄”。

`IsSameSongTitle` 用于严格核心歌名比较：

- 双侧规范化后必须非空且相等，不能以子串包含代替。
- 可清理前置方括号标记。
- 末尾中英文圆括号、或明确的 ` - ` / ` – ` / ` — ` 分隔后缀，仅当属于以下白名单才可清理：

```text
live / liveversion / live版 / remix / remix版 / 伴奏 / 伴奏版 / 现场版 / 剧情版
```

- “朗诵”“古诗诵读”“儿童古诗词”及诗词作者等副标题不能随意忽略。
- 不做通用简繁转换，也不直接以依赖库不对称的名称比较代替本项目判定。

QQ 搜索阶段仍可移除更多括号内容以提高召回；**召回到一个结果，不代表它通过严格同曲过滤**。自动匹配保留历史包含规则，手动展示更严格，不应把此次 UI 规则误写成所有自动候选都已严格同名。

## 5. 综合评分

当前共享评分函数为 `QqMusicLyricsProvider.ComputeMatchScore`。归一化公式：

```text
score = Σ(weight × dimensionScore) / Σ(已计入维度的 weight)
```

| 维度 | 权重 | 当前规则 |
| --- | --- | --- |
| 歌名 | 0.35 | 严格核心同名或规范化完全相等为 1；包含为 `0.6 + 0.4 × min长度/max长度`；否则 0 |
| 时长 | 0.25 | `1 / (1 + (delta / 8000)^2)`；任一时长缺失则不计入，不做时长硬拒 |
| MatchType | 0.20 | `MatchTypeRank / 100.0`；始终计入，未知为 0 |
| 歌手 | 0.15 | 相等、包含或拆分后集合相同为 1；部分交集为 0.6；不匹配为 0.2；期望歌手为空不计入 |
| 专辑 | 0.05 | 相等或包含为 1，否则 0.3；期望专辑为空不计入 |

`MatchTypeRank` 使用 Lyricify.Lyrics.Helper 0.2.0 的枚举名称映射：

| 名称 | Rank | 归一化分 |
| --- | --- | --- |
| Perfect | 100 | 1.00 |
| VeryHigh | 99 | 0.99 |
| High | 95 | 0.95 |
| PrettyHigh | 90 | 0.90 |
| Medium | 70 | 0.70 |
| Low | 30 | 0.30 |
| VeryLow | 10 | 0.10 |
| NoMatch / Unknown / 其他 | 0 | 0 |

不要恢复旧的 `/5.0` 映射、漏掉 `VeryHigh`，或把 PrettyHigh 排在 High 前面。升级依赖时须检查枚举名称，未知名称会静默落到 0。

## 6. 用户选择与缓存

`TrackKey.Of(title, artist)` 仍是普通自动缓存和选择记忆的曲目 key，但已增加候选专用歌词缓存：

```csharp
CandidateCacheKey(key, candidate)
    => $"candidate:{key.Length}:{key}{candidate.SourceKey.Length}:{candidate.SourceKey}{candidate.Id}";
```

成功手选的行为：

1. 取消同曲恢复，开启新的歌词 generation。
2. 按候选来源与 ID 取词；Loaded 后写候选专用缓存和普通曲目缓存。
3. 在选择存储中记忆候选；下一次优先查专用缓存，可离线复用。
4. 旧版只有选择记忆而没有专用缓存时，先重新获取该候选，不能直接相信可能来自旧自动错词的普通缓存。
5. 记忆候选获取失败时仍会退回自动链路；不能把这条降级描述成“手选永久保证成功”。

纯音乐可临时应用，但不写本次手选的持久记忆与歌词缓存，避免一次误选长期挡住自动匹配。手选取词失败也不应关闭窗口或伪装为已成功应用。

当前自动缓存还没有完整的时长、专辑、曲目指纹和算法版本，不能把候选专用 key 视为完整版本化决策缓存。

## 7. 跨请求一致性

- 选择器固定 `LyricsSelectionContext`；曲目 revision 与歌词 generation 独立。
- 搜索期间切歌，旧选择器锁定为过期，不得将旧候选记到新歌；A → B → A 同样失效。
- 手选接管后，同歌自动晚到不得覆盖显示、状态或缓存。
- 每次 await 后不仅保护歌词行，还要保护状态、恢复调度、选择记忆及缓存副作用。
- 取消只代表停止等待和发布，不保证底层 provider 网络操作已停止。

职责与测试入口见 [HANDOVER.md](./HANDOVER.md#5-必须保留的回归约束)。

## 8. 超时与候选窗口

- 自动加载和手动候选聚合均有单源 **5 秒**、总计 **8 秒**预算；剩余总预算不足时按剩余时间等待。
- 某源异常或超时继续后续源；候选查询保留已经取得的结果。
- 按候选取词默认最多等待 **5 秒**。
- 选择器立即显示加载态，支持关闭取消和重新搜索；列表仍在聚合结束或预算耗尽后返回，不是逐源流式展示。

## 9. 已锁定的示例

- “回旋”与“回旋木马”、“黑夜回旋”：严格同曲为 false。
- “星”与“星炬不熄”：不是同歌，且不能通过单字自动包含准入。
- “题都城南庄”与带“古诗诵读 / 朗诵 / 作者”副标题的不同完整标题：不能无差别去括号当作同曲。
- Live / Remix / 伴奏等白名单版本：双侧清洗后核心歌名相等则可展示。
- 同名其他歌手：默认优先正确歌手，勾选后可显示；其他歌即使同歌手也不能展示。

## 10. 验证与改动边界

主要回归入口：`QqMusicMatchingTests`、`QqCandidateSelectionTests`、`MediaInteractionTests`、`LyricsProviderChainTests`、`LyricsGenerationTests`、`LyricsSelectionTests`。最新数量与隔离限制见 [索引](./README.md#最近验证基线)。

调整权重不能替代数据归属修复；取得高元数据匹配度但 NotFound，仍需分别检查取词响应、权限、格式解析与候选 ID，不能只看评分推断接口一定有词。

## 11. 未完成：同名多版本与跨源统一决策

历史案例（2026-09-15）：《七夕 / 银临》实际时长约 `226156ms`，切歌早期却带入上一首的 `286284ms`。候选中的 `244000ms` 版本因此比正确的 `226000ms` 版本更接近错误输入；QQ 返回可加载结果后，串行链不再比较其他源。

当前并未完成时间线快照归属与跨源决策的整体改造，不能宣称上述版本歧义已经解决。

下一步目标，**尚未实现**：

```text
稳定播放元数据 / TrackQuery
  → 多提供器 SearchCandidates
  → 统一 CandidateRanker
  → SelectionDecision（手动 / 自动 / 歧义）
  → 按候选 FetchLyrics
  → 带版本证据的决策缓存
```

必须满足：

- 播放层负责判定时间线是否属于当前歌曲；不可靠时长传空，不把旧 EndTime 当新歌证据。
- 自动与手动共用候选证据和排序器，手动选择优先。
- 决策保存来源、候选 ID、曲目指纹和算法版本，并记录冲突与歧义。
- 证据不足时等待稳定元数据或标记歧义，不静默采用第一个可加载结果。
- **禁止多个 `LoadAsync` 并行竞速、谁先返回用谁**，那是抢答，不是统一匹配。
